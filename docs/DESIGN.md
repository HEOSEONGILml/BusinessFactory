# BusinessFactory 설계 문서

AI 직원들이 사람 대신 일하는 **범용 업무 시스템**. 업무 내용(서비스 대량 생산 등)은 이 시스템에 나중에 부여하며, 시스템 자체는 특정 업무에 종속되지 않는다.

## 1. 전제와 제약

- **비용**: API 과금 없이 Claude 구독 범위 안에서 동작한다.
- **실행 엔진**: Claude Code CLI의 무인 모드(`claude -p`)를 자식 프로세스로 실행한다.
  - Agent SDK는 쓰지 않는다 (공식 문서상 API 키 인증 전제).
  - `--bare`는 쓰지 않는다 (구독 로그인을 읽지 않음). 향후 `-p`의 기본값이 될 예정이므로 버전 업 시 확인.
- **사용량 한도**: 구독은 세션/주간 한도가 있고 병렬 실행이 같은 한도를 나눠 쓴다. 약관상 한도는 "일반적인 개인 사용"을 전제로 하므로 동시 실행 수를 낮게 유지한다.
- **언어**: TypeScript, Node 24의 타입 제거 기능으로 빌드 없이 실행.

## 2. 핵심 원칙

1. **상태는 세션이 아니라 파일에 둔다.** 프로세스가 죽거나 PC를 껐다 켜도 이어서 일한다.
2. **엔진은 판단하지 않는다.** 실행·기록·규칙 강제만 하고, 계획·분해·배정은 AI 직원이 한다. 그래서 어떤 업무든 코드 수정 없이 처리한다.
3. **직원끼리 직접 대화하지 않는다.** 모든 소통은 업무 보드(지시서, 결과물, 로그)를 거친다.
4. **규칙은 AI의 기억이 아니라 도구가 강제한다.** 업무 보드는 반드시 `bf` 명령어로만 바꾸고, `bf`가 회사 규칙을 검사한다.
5. **AI는 스스로 권한을 늘릴 수 없다.** 직원 정의와 시스템 코드는 사람 승인 없이 바뀌지 않는다.

## 3. 구성

```
사용자 ──bf──┐
             ▼
        [업무 보드 (파일)] ◀──bf── AI 직원들
             ▲                    ▲
             │ 읽고 기록          │ claude -p 로 실행
        [엔진 (상주 프로세스)] ────┘
```

### 폴더 구조

```
BusinessFactory/              시스템 (이 git 레포)
  engine/                       엔진 + bf 소스
  bin/                          bf 실행 스크립트 (bf, bf.cmd)
  templates/                    회사 설립 시 복사되는 견본 (핸드북, 기본 직원 4명)
  docs/
  company/                    회사 데이터 (별도 git, 시스템 레포에서 제외)
    config.yaml                 회사 설정
    handbook.md                 직원 공통 규정
    staff/                      직원 명부 (사용자 승인으로만 변경)
    board/T0001/                업무 하나 = 폴더 하나
    hiring/                     채용안 (승인 대기)
    memory/                     회사 기억
    schedules.yaml              정기 업무
    usage.jsonl                 실행별 사용량 기록
  workspaces/                 작업물 (프로젝트마다 독립 git, 시스템 레포에서 제외)
```

`BF_COMPANY` 환경변수로 회사 데이터 폴더를 바꿀 수 있다 (시험용 회사 등).

## 4. 조직

| 직원 | 역할 | 모델 |
|---|---|---|
| 사용자 (owner) | 목표 지시, 결재 | - |
| ceo | 목표 → 계획 → 업무 분해·배정 → 결과 취합 → 보고 | opus |
| hr | 필요한 직무의 직원 정의(채용안) 작성 | opus |
| reviewer | 결과물이 완료 조건을 충족하는지 검수, 미달 시 반려 | sonnet |
| 실무진 | 실제 작업. 처음엔 범용 실무자 1명, 이후 필요 시 채용 | sonnet |

- 위임 깊이 제한: 기본 3 (`config.yaml`의 `max_depth`).
- 직원 정의는 Claude Code 하위 에이전트 형식(`company/staff/<name>.md`). 엔진이 실행마다 `--agents` 파일로 넘긴다.
  - `tools`: 쓸 수 있는 도구 종류
  - `permissions`: 업무 폴더 밖의 추가 권한 규칙 (예: `Bash(npm:*)`, `WebSearch`)
- 모든 직원 실행 시 `company/handbook.md`를 `--append-system-prompt-file`로 주입.

## 5. 업무 보드

### 업무 폴더

```
board/T0012/
  task.md     YAML 메타정보 + 설명 + 완료 조건
  log.md      이력 (덧붙이기만)
  output/     결과물
```

### 메타정보 필드

| 필드 | 의미 |
|---|---|
| id, title | 식별자, 제목 |
| status | 상태 (아래) |
| assignee | 담당 직원 |
| created_by | 지시자 (owner 또는 직원 이름) |
| parent | 상위 업무 id (최상위 목표는 null) |
| depends_on | 선행 업무 id 목록 |
| depth | 위임 깊이 (목표 = 0) |
| review | 검수 여부 |
| workspace | 작업 공간 이름 (없으면 null) |
| project | 소속 프로젝트 (사용량 배분 단위) |
| priority | 우선순위 (클수록 먼저) |
| attempts / max_attempts | 실행 시도 횟수 / 상한 |
| rejections / max_rejections | 반려 횟수 / 상한 |
| ask_to | 질문 대기 시 답할 대상 |
| created_at, updated_at | 시각 |

### 상태

| 상태 | 의미 |
|---|---|
| awaiting_approval | 결재 대기 |
| pending | 대기 (실행 가능 후보) |
| running | 진행 중 |
| waiting | 하위 업무 완료 대기 |
| blocked | 질문 대기 |
| review | 검수 대기 |
| done | 완료 |
| failed | 실패 (재시도/반려 한도 소진) |
| canceled | 취소 |

```
awaiting_approval ──승인──▶ pending ──▶ running ──done──▶ review ──pass──▶ done
                              ▲   ▲        │  │               │
                              │   │        │  └─ask─▶ blocked │
                              │   │        │          │answer │
                              │   └────────┼──────────┘       │
                              │            └─하위 업무 있음─▶ waiting
                              │                                 │ 하위 업무 모두 종료
                              ├─────────────────────────────────┘
                              └──────────── reject ◀────────────┘ (review에서)
```

- **실행 가능 조건**: `pending` 이고 `depends_on` 이 모두 `done`.
- **상위 업무 재기상**: `waiting` 업무의 하위 업무가 모두 종료(done/failed/canceled)되면 `pending`으로 돌려 담당자가 결과를 취합하게 한다.
- **검수**: 기본 켜짐. 상위 직원이 사소한 업무는 `--no-review`로 끌 수 있다. 최상위 목표는 항상 검수.

### 동시성

`bf`와 엔진은 회사 단위 잠금(`company/.lock`)을 잡고 보드를 변경한다. 파일은 임시 파일에 쓰고 이름을 바꾸는 방식으로 원자적으로 저장한다.

## 6. bf 명령어

같은 명령어를 사용자와 AI 직원이 함께 쓴다. 호출자는 환경변수 `BF_ACTOR`(기본 `owner`), 현재 수행 중인 업무는 `BF_TASK`로 식별한다. 엔진이 직원을 실행할 때 두 값을 설정한다.

| 명령 | 설명 |
|---|---|
| `bf init` | 회사 데이터 폴더 생성 |
| `bf goal "<목표>"` | 최상위 목표 생성 (ceo 배정) |
| `bf task create --to <직원> --title ... --done-when ...` | 업무 생성 (BF_TASK가 있으면 그 하위 업무) |
| `bf task show <id>` / `bf task list` | 조회 |
| `bf task done <id> --summary ...` | 완료 보고 |
| `bf task ask <id> "<질문>"` / `bf task answer <id> "<답>"` | 질문/답변 |
| `bf task pass <id>` / `bf task reject <id> "<사유>"` | 검수 통과/반려 |
| `bf task comment <id> "<내용>"` | 로그에 코멘트 |
| `bf task cancel <id>` | 취소 (하위 업무 포함) |
| `bf status` / `bf agents` / `bf usage` | 회사 현황 / 직원 목록 / 사용량 요약 |
| `bf engine [--once]` | 엔진 실행 |
| `bf inbox` | 결재·질문·끝난 목표 모음 |
| `bf approve <id>` / `bf deny <id> "<사유>"` | 결재 승인/반려 (채용 포함) |
| `bf ack <id>` | 끝난 목표 확인 처리 |
| `bf approval request <id> "<내용>" --need "<규칙>"` | 결재 요청 (직원) |
| `bf hire propose <id> <채용안.md>` / `bf hire list` | 채용 제출 (hr) / 대기 채용안 |
| `bf memory list` / `show <주제>` / `add <주제> "<내용>"` | 회사 기억 |

### bf가 강제하는 규칙

- 완료 조건 없는 업무는 생성 불가
- 위임 깊이 초과 불가
- 존재하지 않는 직원에게 배정 불가
- 남의 업무를 완료/질문 처리 불가
- 하위 업무가 진행 중인 업무는 완료 보고 불가
- 검수 통과/반려는 검수자, 지시자, 사용자만 가능 (자기 업무 검수 불가)
- 직원은 자신이 수행 중인 업무의 하위 업무만 생성 가능 (최상위 목표는 사용자만)
- 결재·확인 처리는 사용자만 가능, 범위 없는 권한은 요청 불가

## 7. 엔진

상주 프로세스(`bf engine`, 회사당 하나만 실행). 반복:

1. 사용량 한도 대기 중이면 리셋 시각까지 쉰다.
2. 정기 업무 중 시각이 된 것을 목표로 등록한다.
3. 실행할 업무를 고른다.
   - 검수 대기 업무가 먼저다.
   - 그다음 실행 가능한 업무를 우선순위(업무 + 프로젝트) 순으로 고른다.
   - 동시 실행 상한과 작업 공간당 1명 규칙 안에서 빈 자리만큼 실행한다.
4. 끝난 실행을 처리한다.
   - 직원이 `bf`로 상태를 바꿨으면 그대로 둔다.
   - 하위 업무를 만들고 끝났으면 `waiting`. 하위 업무가 모두 끝나면 `bf`가 상위를 `pending`으로 되돌린다.
   - 아무 보고 없이 끝났으면 재시도 횟수를 차감한다.
   - 사용량 한도 문구(`You've hit your ... limit · resets ...`)가 나오면, 시도 횟수를 쓰지 않고 업무를 `pending`으로 되돌린 뒤 리셋 시각까지 대기한다. 종료 코드는 문서상 정해져 있지 않아 문구로 감지한다.
   - 인증 오류(401/403)가 나오면 엔진을 정지한다.
5. 감시 장치를 확인하고, 이상이 없으면 회사 데이터를 git에 커밋한다. 사용량은 `usage.jsonl`에 기록한다.
6. 재시작 시 `running`으로 남은 업무는 시도 횟수를 쓰지 않고 `pending`으로 되돌린다.

### 직원 실행 방식

```
claude -p --agents <정의.json> --agent <직원> --output-format json
       --permission-mode dontAsk --strict-mcp-config --max-turns N
       --allowedTools <경로 제한 규칙들> --add-dir <허용 폴더>
       --append-system-prompt-file handbook.md        (지시문은 표준입력)
```

- 작업 폴더(cwd)는 그 업무의 폴더다.
- 환경변수 정리:
  - `ANTHROPIC_*`, `CLAUDE_CODE_*`, `CLAUDECODE`를 제거한다. API 키가 있으면 구독 로그인보다 우선하기 때문이다.
  - claude.ai 연결 서비스를 끈다(`ENABLE_CLAUDEAI_MCP_SERVERS=false`).
  - `BF_ROOT`, `BF_COMPANY`, `BF_ACTOR`, `BF_TASK`, `PATH`(bin 포함)를 설정한다.

### 권한 모델 (실험으로 확인)

- 권한 목록에 도구 이름만 넣으면(`Write`, `Read`, `Bash`) **디스크 전체 권한**이 된다. 그래서 절대 넣지 않는다.
- 파일 권한은 경로 규칙으로만 준다.

| 실행 | 쓰기 (`Edit(경로/**)`) | 읽기 (`Read(경로/**)`) |
|---|---|---|
| 업무 실행 | 자기 업무 폴더, 작업 공간 | 업무 보드, 회사 기억 |
| 검수 | 없음 | 해당 업무 폴더, 작업 공간, 업무 보드, 회사 기억 |

- Bash는 `Bash(bf:*)`가 기본이다. 직원 정의의 `permissions`와 결재로 받은 `grants`만 추가된다.
- 직원 정의 파일의 `tools` 줄만으로는 실행 권한이 생기지 않는다. `--allowedTools`가 필요하다.
- **한계**: `Bash(npm:*)`처럼 셸 명령을 허용하면 그 명령을 통해 경로 제한을 벗어날 수 있다. 그래서 감시 장치를 둔다.
  - 실행 후 시스템 영역(`engine/`, `bin/`, `templates/` 등)의 git 상태가 바뀌었으면 엔진을 정지한다.
  - 실행 후 `company/staff/`에 커밋되지 않은 변경이 있으면 엔진을 정지한다. 채용 승인은 승인 시점에 즉시 커밋된다.

## 8. 결재

- 항상 사용자 승인을 받는 일: 채용, 비용 발생, 외부 공개(배포·게시·발송), 계정 생성, 데이터 삭제.
- 직원은 이 권한이 없다. 필요하면 아래처럼 결재를 올린다.
  ```
  bf approval request <업무> "<무엇을, 왜>" --need "<권한 규칙>"
  ```
- 결재를 올리면 업무가 `blocked`(결재 대기)가 된다.
  - **승인**(`bf approve`): 요청 권한이 **그 업무에만** `grants`로 부여되고 `pending`으로 돌아간다. 검수자에게는 부여되지 않는다.
  - **반려**(`bf deny`): 사유와 함께 `pending`으로 돌아간다.
- 범위 없는 권한(`Bash`, `Write` 등)은 요청 단계에서 거부한다.
- **채용 흐름**
  1. hr가 `output/`에 채용안을 쓰고 `bf hire propose`로 제출한다.
  2. 제출 단계에서 검증한다: 이름 형식, 중복 여부, 범위 없는 권한, 지침 길이. 통과하면 `company/hiring/`에 복사한다.
  3. 사용자가 `bf approve`하면 `staff/`로 옮기고 커밋한다.
  4. 사용자가 `bf deny`하면 채용안을 폐기한다.
- 사용자 창구: `bf inbox`에서 결재 대기, 사용자에게 온 질문, 끝난 목표(`bf ack`로 확인 처리)를 한 번에 본다.

## 8-1. 사용자 창구

- **웹 화면** (`npm start` 시 함께 시작, http://127.0.0.1:4300)
  - 목표 등록, 처리할 일(결재·질문·끝난 목표), 업무 트리와 상세(지시서·결과물·이력·활동), 실시간 활동, 구독 사용량, 직원·회사 기억
  - 보안: 127.0.0.1에만 바인딩한다. Host 헤더가 로컬이 아니면 거부한다(DNS 리바인딩 차단). 모든 쓰기 요청은 페이지에 심은 프로세스별 토큰이 필요하다. 결과물 보기는 업무의 `output/` 안으로 제한한다.
  - 실시간: `engine.log` 를 Server-Sent Events로 흘려보내고, 보드가 바뀌면 `changed` 이벤트로 화면을 갱신한다.
- **알림**: Windows 토스트. 선택적으로 ntfy 휴대폰 알림.
- **명령어**: `bf` (직원과 공용)

## 9. 회사 기억

`company/memory/`에 주제별 마크다운과 `index.md`. 직원은 업무 시작 시 목차를 보고 관련 항목만 읽고, 업무 종료 시 배운 점을 `bf memory add`로 남긴다. 반려 사유도 교훈으로 축적한다.

## 10. 대량 생산 대비

- **정기 업무**: `schedules.yaml`에 cron 형식으로 반복 업무 정의, 엔진이 시각에 맞춰 생성.
- **프로젝트 단위 관리**: 업무에 `project` 필드, 프로젝트별 우선순위와 사용량 배분.
- 배포·지표 수집·템플릿은 시스템 변경 없이 직원·도구·회사 기억 추가로 해결.
- 도메인·호스팅·결제 계정 최초 개설은 본인 인증이 필요해 사용자가 1회 수행.
